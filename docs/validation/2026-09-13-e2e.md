# Chat and coding-agent evaluation on the rebuilt backend — 13 September 2026

## Setup

- Machine: RTX 5070 Ti Laptop GPU (12 GB), Windows 11. Bundled `llama-server`
  build 10809 (CUDA). Release build of the backend, scratch data directory,
  frontend served by the backend.
- Models: Qwen3 8B Q4_K_M (native thinking, tools) and Qwen2.5-Coder 14B
  Q4_K_M (no native thinking, tools). Nothing smaller than 8B is on disk, so
  the 2-4B class was not run.
- Harness: `scripts/e2e/e2e.mjs` drives the real HTTP API against the fixture
  project in `scripts/e2e/fixture` (a calculator whose `subtract` adds, a test
  that prints `CALCULATOR_TESTS_PASSED`, and a README with a ticket number).
  The fixture is restored after each run. Timings are the engine's own
  (`timings` object), wall time is the client's.
- Steps: two short chats (the second checks prompt-cache reuse), a code
  answer with Reasoning on (the generated Python is executed), a long answer
  (LRU cache; the old 2,048-token cap), an Ask question in a Code session
  (three files must be read), and an Agent task (fix the bug with a minimal
  edit, run the test, report).

observed across the session.

## What the runs found and what changed

1. **The 14B coder never writes the closing fence.** Every action ended at the
   closing brace of the JSON object and the turn ended there. The strict
   parser rejected all of them as unreadable, so the run only ever progressed
   through the schema-constrained fallback, which then dropped `path`. The
   parser now accepts an action that ends the turn, and the stream stops at
   the closing brace instead of waiting for a fence. It also accepts `json`
   and bare fences that name a registered tool, the `<tool_call>` tag that
   Qwen and Hermes models were trained on, a bare object, `arguments` and
   `parameters` as aliases of `args`, raw newlines inside JSON strings, and
   prose after a closed action. Two actions in one reply stay ambiguous.
2. **Recovery ladder instead of one shot.** An unreadable reply now gets a
   native retry with the format reminder first, then the schema-constrained
   envelope, then the run stops. The failure budget is six consecutive steps
   without a successful action; identical repeats are bounded separately
   (warning at two, stop at five); any successful action resets both.
3. **Feedback on every failure.** Tool errors echo the arguments received; a
   missing `path` names the file the model last worked on; an `edit_file`
   whose `old` text is not found shows the closest lines in the file; an
   ambiguous `old` reports how many times it occurs. A rejected completion
   claim is journaled as the model's own words before the review verdict.
4. **The 8B model's failed first edit was recovered by the loop itself**: the
   failing test output reached the model, it read the file, made the second
   edit and re-ran the test. No host intervention.

## Empty models folder with a saved default model

A second backend instance was started against an empty models folder with
`general.default_model` saved as `qwen3-8b`. Startup succeeds and the folder
stays empty (the demo entry is in-memory only). `GET /api/runtime/policy?
model_id=qwen3-8b` used to answer 404, which the Settings page rendered as
"Could not read runtime configuration"; it now answers 200 with the generic
plan and `missing_model: "qwen3-8b"`, and the Default model field already
says the saved default is unavailable. Loading the demo entry answers 404
with "GGUF not found … Add the file under models/<id>/model.gguf". Nothing
loads a model on startup.

## Follow-up round: routing, documents, machine panel

Reported: "can you tell me a bit about this project" in a Code session showed
"Could not determine the request type". The routing probe
(`scratchpad` script against the real project as the workspace) could not
reproduce it: all four installed models answered `ask` from the model for
that message, `ask` for "what does the backend do?", and `agent` for "fix the
failing test and run cargo test", each within 0.4 to 2.1 s. What changed so
the case cannot recur as an error: the model's decision is read leniently,
the routing wait is 60 s on a GPU and 240 s when the model runs on the CPU,
an unusable decision is logged with its finish reason and text, and the
wording router (`request_router::heuristic_intent`, 150 phrasings under test)
decides instead of a notice. Normal Chat never routes.

Documents (Qwen3 8B, experimental and parked by the owner after this round):
in normal Chat, "make me a spreadsheet of a weekly budget" produced
`weekly_budget.xlsx` and "a short PDF explaining the KV cache" produced a
PDF, both listed in the conversation's Artifacts panel; a plain question
produced no file. The files are plain (text paragraphs, bullet slides, cell
values; no styling, images or charts), and an 8B model reaches them only
through the host's corrections: it tends to write the content into the chat
first and needs the nudge or the deliverable check to produce the file. The first spreadsheet attempt had emitted an
unquoted `=SUM(...)` inside the JSON, which now earns one correction quoting
the parser's error; the PDF spec arrived nested under `content` with `type`
instead of `kind`, which the reader now accepts (it previously rendered a
blank file). In a Code session, "make a short presentation about this
project" is routed to the agent, which read the README and produced
`project_overview.pptx` once the deliverable check refused to accept slide
text in the chat; the Ask path reaches the same file through its one nudge.

Machine panel: the RAM row was hidden by a stylesheet rule on screens under
780 px tall, and the CPU row was replaced by the GPU row whenever a GPU
reported. The rows are now CPU, RAM, GPU, VRAM, with the graphics rows only
when a GPU reports, and nothing hidden for height.
