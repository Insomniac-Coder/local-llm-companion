A proposal to the AI Council · September 2026

The next word should be ours.

Every answer an AI gives is written one word at a time, each word picked by a machine. Today that machine belongs to someone else. We propose running our own: connected to our documents, on our hardware, under our rules.

01 What is an LLM

A machine that has read more than any person ever could

A large language model (LLM) is a program trained on an enormous amount of text: books, websites, manuals, code. It learned one skill extremely well: given some text, predict what comes next. Ask it a question, and it predicts, word by word, what a good answer looks like.

Large

Billions of adjustable numbers, called parameters, tuned during training. They hold everything the model learned.

Language

It reads and writes text: English, Hindi, code, tables. Newer models also read images and audio.

Model

An approximation of patterns in language, not a database of facts. It can sound right and still be wrong.

How large is “large”? Memory needed at 4-bit precision. Green: sizes one of our servers can run.

  1. 8–12B

    ≈5–8 GB · a small GPU

    Llama 3.1 8B, Mistral NeMo 12B. Drafting, summaries, simple questions.

  2. 27B

    ≈17 GB · one GPU

    Gemma 3 27B. Strong at reasoning and writing: the sweet spot for a team server.

  3. 70B

    ≈40 GB · one server

    Llama 3.3 70B, on 1–2 data‑centre GPUs. Most business writing and analysis.

  4. 175B

    ≈100 GB · multi-GPU server

    GPT-3 (2020), behind the first ChatGPT. Today’s 27B open models beat it.

  5. 400B

    ≈240 GB · multi-GPU server

    Llama 4 Maverick. A mixture of experts: only 17B work on each token, so it runs fast.

  6. Frontier

    Vendor data centres only

    GPT-5, Claude, Gemini. Sizes unpublished; estimates run to several trillion.

Engineer's note

Memory for the weights is roughly parameters × bits per parameter ÷ 8. At 16-bit an 8B model needs 16 GB; at 4-bit quantisation about 4.5–5 GB, and a 70B model about 40 GB. Add memory for the conversation itself (the KV cache), which grows with the context length. Mixture-of-experts models such as Llama 4 Maverick (400B total, 17B active per token) must still hold all weights in memory, but only compute with the active ones, so they run at the speed of a much smaller model.

02 How it learns

It learns by guessing the next word, trillions of times

Nobody programs the knowledge in. The model starts as random numbers and improves by guessing, checking against real text, and adjusting itself after every mistake.

  1. Stage 1

    Pre-training: read everything

    It reads a huge slice of the internet, books and code. For every sentence it guesses the next word, compares with the real one, and nudges its numbers so the right word becomes more likely.

    15 trillion+ tokens read by Meta's Llama 3 models. The largest used about 31 million GPU-hours of computing.

  2. Stage 2

    Instruction tuning: learn to be an assistant

    It then studies many thousands of example conversations, written or checked by people: a question, followed by a good answer. It learns to follow instructions.

    Result: it answers questions instead of just continuing text.

  3. Stage 3

    Preference tuning: learn what people prefer

    People, and increasingly other models, compare pairs of answers and pick the better one. The model is nudged towards helpful, honest, safe answers. Reasoning models are also rewarded for correct maths and code.

    Result: the polished assistant you know from ChatGPT or Claude.

Engineer's note

Pre-training minimises cross-entropy loss on next-token prediction with gradient descent over mini-batches of millions of tokens across thousands of GPUs. Stage 2 is supervised fine-tuning (SFT); stage 3 is RLHF or a direct method such as DPO. Reasoning models add reinforcement learning with verifiable rewards (unit tests, exact answers). Meta reports about 30.8 million H100 GPU-hours for Llama 3.1 405B.

The part most people miss

After training, the model is frozen.

It does not learn from your conversations.

Its knowledge stops at a cut-off date.

It has never seen our contracts, code or policies.

It never looks anything up: missing a fact, it invents a plausible one. That is a hallucination.

The fix is not a bigger model. Hand it the right documents at the moment a question is asked, and make it cite them. That is called RAG, and it is the heart of this proposal.

Engineer's note

This is the transformer, with gpt‑oss‑120b's published configuration: an o200k_harmony vocabulary of 201,088 tokens, model width 2,880, 36 decoder layers and a 128K-token (131,072) context. It is a mixture of experts: each layer's feed-forward block holds 128 experts and a router sends every token to 4 of them, so of its 117 billion parameters only about 5.1 billion work on any one token.

Each layer is attention plus that expert block, with residual connections and RMSNorm. Attention is causal and grouped-query (64 query heads share 8 key-value heads); position comes from rotary embeddings (RoPE) on queries and keys, not a vector added to the input. Layers alternate between full-context attention and a 128-token sliding window, which keeps the KV cache small at long context.

Inference has two phases: prefill processes the whole prompt in parallel (compute-bound, thousands of tokens per second on a GPU) and decode generates one token per forward pass (memory-bandwidth-bound: every step reads all active weights). Keys and values of earlier tokens are kept in a KV cache so they are not recomputed. A useful ceiling for decode speed is memory bandwidth ÷ bytes of active weights, which is why quantisation and mixture-of-experts models speed up generation. gpt‑oss‑120b stores its expert weights in MXFP4, about 4.25 bits each, so the whole model fits on one 80 GB GPU.

Output: the last position's final hidden state times the output matrix gives one logit per vocabulary entry; softmax(logits ÷ temperature) makes the probabilities; top-K or top-p sampling picks one.

    Why this matters for us

    The model never looks anything up: missing a fact, it still writes the most plausible words, a hallucination. The fix is not a bigger model or a lower dial but the right documents (RAG), with a low temperature.

    Top-K again in RAG →Search picks the top K passages.
    Engineer's note

    Each candidate's score (logit) z is divided by the temperature before the softmax: p = softmax(z / T). Below 1 the odds sharpen, above 1 they flatten, and as T → 0 sampling becomes greedy decoding: always the top token. Top-k keeps the k most probable tokens, zeroes the rest and renormalises the survivors to sum to 1.

    Top-p (nucleus sampling) keeps the smallest set of tokens whose probabilities add up to p, so the shortlist shrinks when the model is confident and grows when it is not. Min-p keeps tokens with at least a set fraction of the top token's probability. Temperature changes the probabilities but never their ranking, so applying it before or after top-k gives the same result; top-p and min-p cut on the probabilities themselves, so for them the order matters. Repetition, frequency and presence penalties lower the scores of tokens already used. A fixed seed makes sampling repeatable on the same setup, which matters for tests and evals.

    Typical settings: chat about 0.7, often with top-p 0.9 to 0.95; extraction, code and RAG answers 0 to 0.3. A real vocabulary holds tens of thousands to over 200,000 tokens, and a high temperature hands the long tail real probability, which is why a cut-off is normally applied. None of these settings changes what the model knows, only how it chooses.

    • The model does not learn. Memory is re-sent text, not training, kept in our own database under our retention policy.
    • Memory costs tokens. Every turn re-sends the thread, so the harness (the software around the model) trims or summarises long ones.
    • Two kinds of memory. The thread is short‑term; long‑term facts such as “Priya works in Finance” sit in a separate store.
    Engineer's note

    Chat-completion APIs, like the model behind them, are stateless: every call carries the full list of messages, and the model keeps nothing between calls. In LangGraph, memory comes from a checkpointer passed to compile(): InMemorySaver for development, SqliteSaver on a single machine, PostgresSaver in production. Each call names its thread with config={"configurable": {"thread_id": "finance-priya-0412"}}; the graph state is saved after every step, so the next call on that thread, even after a restart (with a database-backed checkpointer), carries on from the saved state. The messages key uses the add_messages reducer, which appends new messages instead of overwriting the list.

    To stay inside the context window, trim_messages keeps the system prompt and the most recent turns within a token budget, or a summarisation node replaces older turns with a short summary. Long-term memory is a separate store (InMemoryStore, PostgresStore) with per-user namespaces such as ("memories", user_id), shared across threads. Prompt caching (prefix caching in vLLM and llama.cpp) makes resending an unchanged start of the thread cheap. Threads and stored facts live in our own database under our retention policy, so deleting a thread deletes the memory. Token counts on the slide are illustrative; retrieved documents would add to them.

      09 Our harness

      The model is the engine. The harness is the rest of the car.

      A harness is the software around the model. It finds the right documents, checks who is asking, decides which tools the model may use, applies our rules and keeps a record. ChatGPT and Claude are harnesses around their vendors' models. Build our own, and every one of those decisions is ours.

      • Which model runs, and when to upgrade it. Swapping models is a settings change; answers stay grounded.
      • What it can read: our documents, so it answers from sources and cites them instead of guessing.
      • Who may see what: checked on every answer. A rule in the prompt can be talked around; access rights cannot.
      • What it can do: which tools it may use, such as a live HR lookup, and which actions need a person's approval.
      • What it remembers: an audit log of who asked what and which sources were used, kept as our policy says.
      • How it is measured: our own test questions, run before every change. No per-question bill.

      Example: a salesperson asks “How many leave days do I have left, and what does my manager earn?” A bare model guesses both. With our harness it answers the first from the HR policy and the live HR system, with sources; declines the second, because salaries are restricted to HR; and logs both.

      Engineer's note

      Target architecture: an inference server (vLLM for many users, llama.cpp for small machines) behind an OpenAI-compatible API; an ingestion service with connectors, chunking, embeddings, hybrid search and a reranker; a policy layer that enforces single sign-on identity and document permissions at retrieval time; tools exposed through MCP servers with an allow-list and human approval for write actions; defences against prompt injection in retrieved content; an evaluation set of real questions run on every model or prompt change; and tracing of every request. Because the harness talks to models through one API, swapping the model is a configuration change.

          Engineer's note

          Chunking. Split on headings and paragraphs with a recursive splitter (LangChain's RecursiveCharacterTextSplitter; MarkdownHeaderTextSplitter keeps section titles as metadata), usually 300–800 tokens with 10–20% overlap. Chroma's default embedding model, all-MiniLM-L6-v2, reads only the first 256 word pieces of a text, so with it we keep chunks near 200 tokens; models with longer inputs (EmbeddingGemma up to 2,048 tokens, nomic-embed-text up to 8,192) take the larger sizes. Store the section title, source and page with every chunk so answers can cite them.

          Embeddings. all-MiniLM-L6-v2 turns any text into 384 numbers and runs comfortably on a CPU; EmbeddingGemma and nomic-embed-text (768 numbers each) are stronger options. All of them run on our own servers. Documents and questions must go through the same model; switching models means re-embedding the collection.

          ChromaDB. Open source (Apache 2.0). Runs inside the application with PersistentClient (saved to disk) or as its own server on our machines (chroma run, HttpClient). A collection holds ids, embeddings, documents (the chunk text) and metadata, searched through an HNSW index; we set the collection's space to cosine (the default is squared L2), and the scores shown are 1 − cosine distance. Access control is a metadata filter applied inside the search: query(query_texts=[q], n_results=3, where={"access": {"$in": groups}}), with the groups taken from the person's sign-in, never from the model. When a document changes, upsert its chunks by id and delete the ones that no longer exist; nothing is retrained.

          Getting it right. Hybrid search (keyword BM25 alongside the vectors, merged with reciprocal rank fusion) and a reranker (a cross-encoder that rescores the top 20 to 50) raise precision. Measure retrieval with a test set of real questions and the chunk that answers each: hit rate at K is the share whose right chunk is in the top K. LangChain's Chroma vector store wraps the same collection as the retriever our RAG agent uses (next slide).

            Why LangGraph, not a chain

            LangChain supplies the standard parts: connectors to our private model, the ChromaDB retriever, tools. LangGraph wires them into a graph.

            • Cycles

              It can loop back to retry, refine or ask another agent. A chain only runs forward.

            • Explicit state

              One shared, typed state that every agent reads and writes, saved after every step.

            • Conditional routing

              The next step is chosen from the state at run time, not fixed in advance.

            • Reliability

              Retries, timeouts, fallbacks and resumable runs: one failure no longer breaks everything.

            Engineer's note

            The proof of concept is a LangGraph StateGraph(State). The state is typed: messages, a list merged by the add_messages reducer, and next, the agent to run. The supervisor node calls our private model (gpt-oss-20b) with structured output, so it can only answer rag_agent, infra_agent, general_agent or FINISH; add_conditional_edges routes on next, and every agent has an edge back to the supervisor, which is what makes the loop. LangChain's ChatOpenAI(base_url=…) points every node at the OpenAI-compatible API of our own model server.

            Each sub-agent is a prebuilt ReAct agent (create_react_agent; create_agent in LangChain 1.0). The RAG agent's tool is a ChromaDB retriever with all‑MiniLM‑L6‑v2 embeddings; the Infra agent's tools wrap approved runbooks and APIs (get_metrics, get_logs, restart_service, scale_service); the General agent has none. A checkpointer saves the state after every step under a thread_id, which gives memory and resumable runs; recursion_limit stops a run that loops too long; an interrupt before every infra write action hands the decision to a person: an admin on staging, the on-call engineer on production (next slide); and LangSmith traces every node (two slides on). Models and figures shown are illustrative.

              Engineer's note

              LangGraph can pause a run in two ways, and both need a checkpointer, which saves the run's state under its thread_id. Called inside the node that is about to act, interrupt() stops the run and the caller gets an __interrupt__ payload describing the proposed change: that is what the approval screen shows. The decision resumes the same thread with graph.invoke(Command(resume={"action": "edit", "replicas": 3}), config) and arrives as the return value of interrupt(). On resume the node runs again from its top, so call interrupt() before any side effect.

              A static breakpoint, interrupt_before=["execute"] at compile time, instead stops the run before that node; an edit is written into the saved state with graph.update_state, and graph.invoke(None, config) continues. Because the checkpoint lives in a database (SQLite or Postgres), a restart while waiting loses nothing. In production, add a timeout and escalation for unanswered approvals and record who approved. The pause, the decision and the resume all appear in the run's LangSmith trace; the next slide shows one: a staging restart that an admin approved.

                  Engineer's note

                  Tracing is switched on with LANGSMITH_TRACING=true and an API key (LANGSMITH_API_KEY), plus LANGSMITH_ENDPOINT pointing at a self-hosted instance. LangChain and LangGraph runs are traced automatically; any other function can be added with the @traceable decorator. Each request becomes a tree of runs (chain, LLM, tool, retriever) with inputs, outputs, timings, token counts and errors; tag runs with metadata such as thread_id, user and department to filter and group them.

                  Dashboards and alerts cover latency, tokens, cost and error rates; user feedback can be attached to runs; saved runs become datasets for evaluations, so a new model or prompt is scored on our own questions before it goes live. Self-hosted LangSmith is offered on the Enterprise plan, inputs and outputs can be masked for sensitive data, and traces can also be exported over OpenTelemetry. Open-source alternatives such as Langfuse can be self-hosted too. Every LLM run records the model it used, so speed and cost can be compared model by model; the harness can then send each kind of step to the smallest model that does it well. The models shown (gpt-oss-20b for routing and short replies, gpt-oss-120b for tool use and grounded answers, Gemma 3 27B for drafting, all-MiniLM-L6-v2 for search embeddings) are examples of open-weight models we can host.
